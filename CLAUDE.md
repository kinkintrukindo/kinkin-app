## What This App Is

An internal business management tool for **Kin Kin Trukindo, Ltd.**, a small freight and logistics company in Indonesia. It tracks trips, expenses, cash flow, loans, and fleet assets for a two-truck operation. The interface is in English but all monetary values are in Indonesian Rupiah (IDR).

Live URL: [kinkintrukindo.com](https://kinkintrukindo.com)
App password: stored as `APP_PASSWORD` constant in `src/App.jsx`

## Architecture

**Everything lives in one file: `src/App.jsx` (~4100 lines).**

There is no routing, no state management library, no component library. All state lives in `KinKinApp` (the root component) and is passed down as props. All persistence is through two async functions: `loadState()` and `saveState()`.

```
App (login gate)
└── KinKinApp (all state, all data)
    ├── Dashboard
    ├── Trips
    ├── Expenses
    ├── Kas (Cash)
    ├── PettyCash
    ├── Fleet
    │   └── (sub-tabs: Fleet & Loans, Capital Injections)
    ├── BusinessMetrics  ← embedded inside Reports
    └── Reports
```

### Persistence Pattern

```js
// Load on mount
loadState()  →  supabase.from("kinkin_state").select("value").eq("key", "kinkin_v1")

// Save on every state change (debounced by React's render cycle)
saveState()  →  supabase.from("kinkin_state").upsert({ key: "kinkin_v1", value: entireState })
```

The entire app state is serialized as one JSON blob. There are no relational queries. The `_skipSave` ref prevents a redundant write on the initial load.

### Login

`LoginGate` wraps the entire app. It checks the entered password against `APP_PASSWORD` (a hardcoded constant in `src/App.jsx`). There is no Supabase Auth — authentication is purely client-side. This is acceptable for a private, single-company internal tool.

## Data Models

All IDs are generated by `genId()` — a random 7-character alphanumeric string.

### Trip
```js
{
  id: string,
  date: "YYYY-MM-DD",
  invNo: string,          // invoice number
  destination: string,   // e.g. "Tanjung Priok"
  nopol: string,         // truck plate, e.g. "B9674UEJ"
  contNo: string,        // container number — primary deduplication key
  sangu: number,         // driver allowance (Rp)
  lainItems: [{ label: string, amount: number }],  // extra costs (kept for import)
  lainLabel: string,     // consolidated label for display
  lainAmt: number,       // consolidated extra cost amount
  total: number,         // sangu + lainAmt (total driver cost)
  jual: number,          // invoice amount to client (revenue)
  profit: number,        // jual - total
  source: "import" | "manual",
}
```

**Profit formula:** `profit = jual - (sangu + lainAmt)`

### Expense
```js
{
  id: string,
  date: "YYYY-MM-DD",
  category: string,      // see CATEGORY COLORS section in App.jsx
  description: string,
  amount: number,
  expenseType: "truck" | "overhead" | "petty",
  truck: string,         // nopol, only for expenseType === "truck"
  vendor: string,        // only for expenseType === "overhead"
  holderId: string,      // petty cash holder id, or "unassigned" if imported with multiple holders
  source: "import" | "manual",
  _fpKey: string,        // deduplication key for imported expenses: "EXP:{monthYear}|{LABEL}|{amount}"
}
```

### Kas (Cash Ledger Entry)
```js
{ id, date, description, amount, type: "in" | "out" }
```

Cash balance = sum of all "in" minus sum of all "out".

### Capital
```js
{ id, date, source, description, amount, type: "capital" | "loan" }
```

`type: "capital"` = owner equity injection (does not need to be repaid).
`type: "loan"` = borrowed money (not a truck installment — those live in `loans`).

### Loan
```js
{
  id, lender, purpose, truckId,
  vehicleValue: number,   // full vehicle price
  principal: number,      // loan amount (same as vehicleValue here)
  monthlyPayment: number,
  startDate: "YYYY-MM-DD",
  termMonths: number,
  notes: string,
}
```

Remaining balance = `principal - sum(loanPayments where loanId matches)`.

### LoanPayment
```js
{ id, loanId, date, amount, note, kasId? }
```

`kasId` — ID of the linked `kas` "out" entry created at the same time. Present on all payments recorded after May 2026. Older payments loaded from the database may not have this field; edit/delete gracefully no-ops on kas in that case.

### Asset
```js
{
  id, name, assetType,
  nopol: string,          // truck plate
  purchaseDate, purchasePrice,
  financedBy: string,     // loanId or ""
  status: "active" | "inactive",
  notes,
}
```

### PettyHolder
```js
{ id, name, active: boolean, notes }
```

### PettyTopup
```js
{ id, holderId, date, amount, note }
```

Holder balance = `sum(topups) - sum(expenses where holderId matches)`.

### ImportLog
```js
{
  id,
  importedAt: ISO string,
  fileName: string,
  monthYear: "YYYY-MM",
  truckPlate: string,
  tripIds: string[],      // IDs of trips created by this import
  expenseIds: string[],   // IDs of expenses created by this import
  summary: {
    tripCount, skippedDuplicates,
    expenseCount, skippedExpenses,
    totalRevenue, totalCosts, totalExpenses,
  },
}
```

## Business Rules

### Trip Deduplication (on import)
`fingerprint(trip)` returns:
- `CONT:{containerNumber}` if container number is present — container numbers are physically unique
- `ALT:{date}|{nopol}|{destination}|{jual}` fallback if no container number

Trips that already have a matching fingerprint in existing data are silently skipped.

### Expense Deduplication (on import)
`_fpKey = "EXP:{monthYear}|{LABEL_UPPERCASE}|{amount}"`

Expenses with a matching `_fpKey` are silently skipped.

### Petty Cash Flow
A petty cash top-up creates **two entries simultaneously**:
1. A `PettyTopup` record (tracked under the holder)
2. A `Kas` entry of `type: "out"` (deducted from main cash balance)

This means petty cash disbursements are reflected in the main cash ledger automatically.

When adding an expense of `expenseType: "petty"` from the Expenses tab, the same double-entry happens.

When importing expenses with only one active holder, they are auto-assigned to that holder (`holderId = activeHolders[0].id`). With multiple active holders, imported expenses get `holderId = "unassigned"` and must be manually assigned from the Petty Cash tab.

### Loan Payment Cash Flow
Recording a loan payment via `addPayment()` in the `Fleet` component creates **two entries simultaneously**:
1. A `LoanPayment` record (with a `kasId` field pointing to the kas entry)
2. A `Kas` entry of `type: "out"` (description: `"Loan payment — {lender}{· note}"`)

This mirrors the petty cash double-entry pattern. Editing a payment also updates the linked kas entry's date and amount. Deleting a payment also removes the linked kas entry (keyed by `kasId`).

`Fleet` receives `kas` and `setKas` as props from `KinKinApp` for this purpose.

### Loan Balance
Computed on-the-fly: `principal - sum(payments for this loan)`. Not stored — derived from `loanPayments`.

### Cash Balance
`kas.reduce((s, k) => s + (k.type === "in" ? k.amount : -k.amount), 0)`

Computed on every render from the full ledger. Not stored.

## Import Flow (Excel/CSV)

1. User clicks "Import Excel Sheet" on Dashboard → triggers hidden `<input type="file">`
2. `handleGlobalImport` opens the upload modal, pre-fills current month
3. User confirms the month/year → `proceedWithUpload` reads the file
4. For `.csv`: `parseCSV()` → `parseMonthlySheet()`
5. For `.xlsx/.xls`: `xlsx.read()` → first non-empty sheet → `parseMonthlySheet()`
6. `parseMonthlySheet()` locates two sections by header keywords:
   - **Trips**: starts at row after `NO, TANGGAL MUAT, ...` header; ends at `TOTAL` row
   - **Expenses**: starts two rows after `PENGELUARAN TAMBAHAN` label; ends at `TOTAL` row
7. Preview modal shows parsed trips and expenses — all fields are editable before committing
8. On confirm: deduplicate, auto-assign petty holder, append to state, create `ImportLog`
9. Import can be fully undone from Dashboard → Import History → 🗑 Undo

## Coding Conventions

- **All styling is inline.** No external CSS classes are used (except the single `<style>` tag in `KinKinApp` for global resets and scrollbar). When adding UI, write `style={{ ... }}` objects.
- **No TypeScript.** Plain `.jsx` only.
- **No router.** Tab switching is a `useState("dashboard")` string.
- **No comments on what the code does.** Only comments explaining why something non-obvious exists.
- **Currency formatting** uses `fmt(n)` — always IDR, no decimals.
- **Date format** is always `"YYYY-MM-DD"` (ISO). The `today()` helper returns this.
- **IDs** are always generated with `genId()` — never use timestamps or sequential numbers.
- **Toast notifications** use `showToast(message, type)` — `type` is `"success"` (default) or `"error"`.
- **Confirmation dialogs** use the `confirmModal` state pattern — never `window.confirm`.
- **Color palette**: gold `#c8a86b` (brand), dark bg `#0d0d0d`, card bg `#161616`, green `#10b981` (positive), red `#ef4444` (negative/warning), amber `#f59e0b` (expenses).

## What NOT to Do

- Do not split `App.jsx` into multiple files unless explicitly asked.
- Do not add TypeScript, a CSS framework, a router, or a state management library.
- Do not add `console.log` statements outside of error paths.
- Do not add features beyond what the user requests — this is a lean internal tool.
- Do not use `window.localStorage` — persistence is Supabase only.
- Do not use `window.confirm` or `window.alert` — use the `confirmModal` / `showToast` patterns.
- Do not seed Supabase with `scripts/seed.mjs` if the database already has data — it checks first, but be aware.
